# workflow
- Only implement changes explicitly requested; do not refactor, rewrite, or add features beyond what the user asked for. Confidence: 0.85
- In the extension browser UI, group available extensions by source/repo (e.g., Mihon repos, mangayomi repos), not by language. Each repo gets its own collapsible section so users can see which source each extension comes from. Confidence: 0.90
- Filter the extension browser language scope to a curated whitelist: only show extensions for All, English, Spanish, French, Italian/Latin, and Dutch. Do not show every available language. Confidence: 0.85
- When adding new features that coexist with existing functionality (e.g., supporting a second extension ecosystem), implement in a way that does not break existing features — isolation and backward compatibility are explicit requirements. Confidence: 0.85
- When the user reports a bug, they provide full stack traces and exact reproduction steps (including before/after behavior like "works after fresh install, fails after restart"). Always trace the exact code path using the provided stack trace — do not guess at the root cause. Confidence: 0.80
- The user reports bugs as systemic/cross-cutting issues affecting all extensions (e.g., "in most plugins there are 2 issues"), not as individual bugs in one extension. Always look for a root cause in the shared infrastructure layer (bridge code, network setup, state persistence, URL handling) rather than in individual extension code. Confidence: 0.75
- When porting a feature from a reference codebase, implement the exact same architecture, patterns, and code structure ("same code and pattern") — avoid simplified reimplementations or shortcuts. Faithful verbatim porting is preferred. Do not assume or reimplement in a different way from the reference. Confidence: 0.90
- For extension/integration layer features (plugin loading, source registration, native bridge communication, OkHttp client setup), reference **Mihon's** implementation as the authoritative source — the app's extension support is built on Mihon's architecture, not mangayomi's. Mangayomi extensions are a secondary/separate ecosystem to support later. Confidence: 0.90
- The long-term goal is to support both Mihon-type extension sources and mangayomi-type extension sources as separate ecosystems. Confidence: 0.85
- When fixing bugs in ported code, the first step must be to re-examine the reference codebase (mangayomi) as the authoritative source of truth — understand how it solves the same problem end-to-end before writing any fixes. The reference is not just for initial porting but for all ongoing debugging and decision-making. Confidence: 0.90
- Remove non-functional features rather than leaving broken toggles/settings in place. When a user reports a UI element "seems to have no effect", remove it — don't try to make it functional unless explicitly asked. Confidence: 0.85
- Study and deeply understand existing code architecture before implementing — the user expects thorough research of how a feature works end-to-end before any changes are made. Confidence: 0.85
- Never make assumptions about how mangayomi implements a feature. Always read the actual mangayomi source files to verify the exact implementation before writing any code. "NO ASSUMPTIONS!" is a hard rule — do not guess or infer mangayomi's behavior. The user has explicitly emphasized "DO NOT ASSUME ANYTHING" — this is the highest-priority rule. Confidence: 0.97
- When implementing multi-feature projects, build from the fundamental/foundational layer upward. Start with the core model and data layer changes, so each subsequent feature builds on a solid base — never implement surface-level features first and hack them into place later. This prevents breaking existing functionality and avoids messy workarounds. Confidence: 0.85
- The local database should be the authoritative source of truth for all display data, not raw network API responses. Network data should be used only to populate/update the DB, and the UI should always read from the DB. Prevents issues where extensions return incomplete or misaligned metadata. Confidence: 0.80
- Extension crashes must be caught and wrapped: the `UncaughtExceptionInterceptor` (first in the OkHttp chain) should catch any non-`IOException` exception thrown by extension code and re-throw it as an `IOException`, preventing the extension from crashing the host app. Confidence: 0.85
- The default OkHttpClient for extensions must match Mihon's timeout values exactly: 30s connect/read/write timeouts and a 2-minute call timeout. Do not use shorter timeouts or omit the call timeout. Confidence: 0.80
- Extension cookie persistence should use `AndroidCookieJar` backed by Android's WebKit `CookieManager`, matching Mihon's implementation. This fixes 419/session-expired errors by maintaining sessions across extension requests. Confidence: 0.80
- The default client must include a `UserAgentInterceptor` that sets a `Mozilla/5.0` user-agent only when the extension hasn't already set one. This fixes 403 errors from sites that block non-browser clients. Confidence: 0.80
- Extension lib version validation should use an explicit list of supported versions matching Mihon's current range (e.g., `listOf(1.4, 1.6)`) rather than a min/max range. This ensures the bridge stays tightly aligned with what Mihon actually supports. Confidence: 0.75
- Installed extension tiles should navigate to the source browse screen (manga grid) as their primary tap action, not to an extension detail/info screen. The detail/version/uninstall screen should be accessible only via a secondary action (e.g., an info icon button on the tile). Confidence: 0.85
- When debugging issues that involve remote data formats (e.g., index JSON schemas, API response shapes), verify the actual payload by fetching it from the live endpoint — do not infer the schema solely from code models, type definitions, or assumptions about what fields should exist. The real JSON is the authoritative source of truth for field names and structure. Confidence: 0.80
